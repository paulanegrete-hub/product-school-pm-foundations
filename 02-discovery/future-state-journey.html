RouteLogic Velocity · Future-state journey

The dispatcher runs the day from one tool again

A live re-route goes from five manual steps across four tools to four stages inside Velocity. This is the target experience, a hypothesis to validate, built on the Module 2 research.

Persona
Fleet dispatcher (primary) and delivery driver (co-persona)
Goal
Seamless orchestration of route management
Friction
The product is paid for but has lost the job of running the day
Strategy
Strip legacy noise and make every change reach the driver in seconds

Four stages of a live re-route

Each user action is written as Action → Benefit.

  1. 1

    Spot the exception

    User action

    Live board flags the late stop → spots it without asking in chat

    Internal state

    “I can see it. I don't have to ask.”

    Pain point addressed

    Board lags 20–60 min, shows delivered stops as “in progress” BUG-2072 · UXR-09

  2. 2

    Re-route in one move

    User action

    Drags the stop to a nearby driver from home → no menus to dig through

    Internal state

    “That was one step.”

    Pain point addressed

    Core actions buried 2–3 levels deep under features nobody uses BUG-2079 · UXR-04 · UXR-11

  3. 3

    The driver gets it now

    User action

    Change pushes to the driver, who taps accept → confirmed in seconds

    Internal state

    “Done once, and it landed.”

    Pain point addressed

    8–15 min lag, no push, so every change is re-sent in WhatsApp BUG-2044 · UXR-02

  4. 4

    Trust the board

    User action

    Driver closes the stop in one tap → board updates live

    Admin reporting sits one layer away → enterprise value kept, noise gone

    Internal state

    “The board is the truth. I can mute the WhatsApp group.”

    Pain point addressed

    3 screens to mark delivered, so confirmations come by text BUG-2055 · UXR-01 · UXR-12

Today: the workaround

  • Reassign in RouteLogic, then re-send in WhatsApp
  • Collect confirmations by text
  • Check status in chat, not on the board
  • Recover crashed routes by phone

5 manual steps · 4 tools · 8–15 min until the driver sees it

Velocity: the future state

  • Spot, re-route, confirm and close in one workspace
  • Driver confirms with one tap
  • The board is the record
  • Enterprise features one layer away, not removed

4 stages · 1 tool · target: seconds to the driver

Three advantages over the manual workaround

  1. One entry, not twoA change made once reaches the driver. WhatsApp always needs a second send.
  2. One record everyone trustsLive status replaces chat threads nobody can search, audit or hand over between shifts.
  3. It feeds what customers pay forTaps land in the admin reporting that sold the product (UXR-10). Texts never do.

Dependency: stripping legacy noise fixes stages 2 and 4. Stage 3, the heart of the hook, needs the sync fix behind BUG-2044, which is why reliability is part of the strategy.

Out of scope: mid-route crashes (BUG-2031), offline mode (BUG-2050) and photo upload failures (BUG-2061). They hurt the driver but don't cause the re-route loop. Crash rate is tracked as a guardrail.

Sources: Module 2 user research (UXR-01 to UXR-12) and bug reports (BUG-2031 to BUG-2090). Internal states are written as the target experience, not research quotes. “Seconds” is a target, not a measured figure.
